## Идеи

Идеи 1–5 и 15 относятся к **пайплайну (цепочкам шагов)**, которого в коде пока
нет: это фаза 11 `docs/roadmap.md`. Идеи 6–14 — к существующим инструментам и
UI. Оценки (S/M/L) — оценка труда, не приоритет.

1. **Менять первый инструмент цепочки** — оценка M. Сейчас базовый инструмент
   зафиксирован при открытии страницы; хочется заменить его на другой без
   разборки цепочки: шаги и их параметры сохраняются, вход перечитывается.
   Открытый вопрос: что делать с несовместимыми параметрами (text-source ↔
   file).

2. **Сворачивать инструменты в chain** — оценка S. Тоггл сворачивания звена до
   заголовка «Шаг n: название» (превью скрываются). Состояние свёрнутости
   помнить в workspace-pipeline.

3. **Несколько цепочек: сохранение и загрузка** — оценка M. Именованные цепочки
   в localStorage (список, создать/переименовать/удалить), быстрое переключение.
   Формат экспортного JSON расширить опциональным полем имени; обратной
   совместимости со старыми выгрузками не делаем (см. задачу про `id`/`slug`
   выше — формат ещё не устоялся).

4. **Batch-обработка архивов выбранным chain** — оценка L. Вход — zip-архив
   картинок (распаковка в браузере), прогон текущего или выбранного сохранённого
   chain по каждому файлу, сборка результата обратно в zip для скачивания.
   Зависит от идеи 3 (выбор цепочки) и от экспортного формата pipeline JSON;
   прогресс и ошибки — пофайлово.

5. **Избранные инструменты (fav tools)** — оценка S/M. Тоггл-звёздочка на
   карточках каталога, результатах поиска и в шапке страницы инструмента; список
   id в localStorage. Избранное показывается отдельной секцией сверху каталога и
   поднимается в выдаче поиска (бонус к popularity при скоринге).

6. **Конвертация формата — НЕ отдельный инструмент, а выбор в кнопке Download**
   — оценка M/L. Решение и продуктовое обоснование: `docs/plan-seo.md` §0 и
   задача **S1f**; почему селектор не заменяет существующие convert-страницы —
   `docs/plan-seo.md` §5. Механическая часть уже есть: `ToolEntry.output`
   (`OutputFormat`: mime/ext/qualityParamId) и кодирование по нему в
   `SchemaToolView.download()` — `docs/architecture.md`, раздел 3. Что осталось
   сверх S1f:
   - экспорт с лимитом размера → закрывает отложенный `reduce-to-size-png`
     (целевой KB, бинарный поиск по k из квантования). Проработать вместе с
     достройкой download-флоу.

7. **`watermark-image-png` (водяной знак картинкой)** — оценка M. Нужна
   overlay-механика: второй источник изображения (getOverlay/store), параметры
   scale/opacity/position/margin/aspect. Решается вместе с вопросом, как второй
   источник картинки вписывается в schema-driven preview (`SchemaToolView`).

8. **`png-info` (детальная информация о PNG)** — оценка M/L. Отдельный райз:
   exif-теги, редактирование, структурированный вывод; нужен свой отдельный
   случай в UI, не «ещё один text/verdict». Возможно нужна вообще отдельная
   страница, несовместимая с другими инструментами: 1) она работает не с
   изображением, а с метаданными из файла, 2) она не может быть частью цепочки,
   т.к. результат не является изображением, 3) если надо изменить теги, никакого
   форматирования и изменения в изображение вносить не надо, только в
   метаинформацию.

9. **Region-инструменты** (censor/erase/pixelate-area/blur-area/sharpen-area/
   reverse-area) — ждут UI выделения области на превью. Вне очереди.

10. **Мультифайловые инструменты-потребители** (gif-to-frames, separate-colors)
    — механизм «результат = набор файлов» (1 → many) уже есть
    (`docs/architecture.md`, раздел 7), первый потребитель —
    `split-into-parts-png`. Остальные подключаются по мере нужды.

11. **Анимационные** (slow-reveal/fade/scrolling) — выход не PNG; отдельное
    решение о формате.

12. **HARD-серия** (glitch, barcode, signature-extract, handwritten-digital).

13. **Контраст текста на акцентных кнопках — частично закрыт**. Тона
    `--color-main`/`--color-accent` подняты под текущий порог `palette.test.ts`;
    targeted-тест проходит. Light-тема всё ещё ниже AA 4.5 для обычного текста,
    а `--color-danger` в light-теме на границе: после завершения редизайна
    вернуть порог 4.5 и перепроверить оба токена.

14. **Отображение маски для инструментов (`runMask`)** — придумать и реализовать
    процесс показа маски результата. **Контекст:** удалённый UI-v1 умел
    показывать ч/б превью-маску «что будет вырезано» отдельным полем; при
    переходе на единый `run(ctx)` этого поля не осталось — executor и
    schema-превью зовут `run()` напрямую, маска не возвращается. **Идея 1:**
    дать каждому `run` возможность вернуть (или инструмент — объявить) `runMask`
    — ч/б изображение маски изменений либо иной подход (отдельное поле `mask` +
    функция маски, второй результат, overlay). Оценка — на усмотрение при
    проработке (S/M). Пока живём без неё. **Идея 2:** каждый `run` возвращает
    два изображения — для отображения (показывает маску или сам результат) и для
    передачи в следующий инструмент (всегда результат). Оценка — на усмотрение
    при проработке (S/M). Пока живём без неё. Первые кандидаты на маску:
    `remove-color-from-png`, `remove-background-png`.

15. **Набор файлов в пайплайне: 1 → many не должен быть терминальным** — оценка
    L. **Сейчас** `execute` принимает один `source: PixelImage | undefined` и
    возвращает один `ToolResult`, а `SchemaToolView` раскладывает вывод в
    `result` / `fileResult` / `textResult` по `resultKind` — поэтому шаг с
    `result: "files"` упирается в конец цепочки. **Направление:** следующий
    инструмент применяется **ко всем картинкам** предыдущего результата
    (fan-out), а many → 1 (вход = архив или несколько файлов) — обратная сторона
    того же контракта. Терминальными остаются только результаты, которые не
    картинка (text, verdict). Что обдумать:
    - где проходит граница: один вызов `run(ctx)` на файл (имя части склеивается
      в `FileResult.files`) или батч целиком на стороне исполнителя;
      `executor/protocol.ts` `files` уже сериализуются, но при батче нужен
      прогресс и отмена;
    - частичные ошибки: один битый файл не должен ронять весь шаг — нужен
      per-file отчёт, а не один `ToolError` на шаг;
    - имена частей на каждом шаге и Download для набора (сейчас zip по
      `tool.id`, `SchemaToolView.download()`);
    - обратная сторона: распаковка zip в браузере, порядок файлов, поведение
      many → 1 → many в одной цепочке. Зависит от идеи 10 (остальные потребители
      1 → many) и идеи 4 (batch по архиву), `docs/roadmap.md` фаза 8
      «batch-страница».

16. **Главная должна отличаться от каталога** — оценка S. Сейчас
    `src/routes/+page.svelte` и `src/routes/list-tools/+page.svelte` побайтово
    идентичны (совпадают script, шаблон и стили), при этом `/list-tools` —
    рабочий маршрут: на него ссылается крошка в `+layout.svelte` и он открыт
    e2e-сценариями `catalog.spec.ts`, `i18n.spec.ts`, `navigation.spec.ts`.
    Замысел: главная — крупнее и с более простым поиском, без категорий; каталог
    остаётся группировкой с фильтрами. Детектор дублирования разметки
    сознательно не вводим — `docs/decisions.md`, раздел 1, поэтому расхождение
    ловится на ревью.

- [ ] **Идея 1. Заменить инструмент шага без удаления** — оценка M. В заголовке
      карточки шага кнопка «поменять инструмент»: заменяет инструмент на месте

- [ ] **Идея 2. Сворачивать инструменты в chain** — оценка S. Тоггл сворачивания

- [ ] **Идея 3. Несколько цепочек: сохранение и загрузка** — оценка M.
      Именованные цепочки в localStorage (список, создать/переименовать/
      удалить), быстрое переключение. Формат экспортного JSON расширить
      опциональным полем имени; обратной совместимости со старыми выгрузками не
      делаем — формат не устоялся: он появится вместе с фазой 11

      со списком всех цепочек: удалить, переименовать, добавить новую,
      «использовать» (переход на страницу инструмента с этой цепочкой). На
      странице — упрощённый вид: только список инструментов цепочки, без
      реального выполнения и параметров.
- [ ] **Идея 4. Batch-обработка архивов выбранным chain** — оценка L. Вход —
      zip-архив картинок (распаковка в браузере), прогон текущего или выбранного
      сохранённого chain по каждому файлу, сборка результата обратно в zip для
      скачивания. Зависит от идеи 3 (выбор цепочки) и от экспортного формата
      pipeline JSON; прогресс и ошибки — пофайлово.
- [ ] **Идея 15. Набор файлов в пайплайне: 1 → many не должен быть
      терминальным** — оценка L. **Сейчас** `execute` принимает один
      `source: PixelImage | undefined` и возвращает один `ToolResult`, а
      `SchemaToolView` раскладывает вывод в `result` / `fileResult` /
      `textResult` по `resultKind` — поэтому шаг с `result: "files"` упирается в
      конец цепочки. **Направление:** следующий инструмент применяется **ко всем
      картинкам** предыдущего результата (fan-out), а many → 1 (вход = архив или
      несколько файлов) — обратная сторона того же контракта. Терминальными
      остаются только результаты, которые не картинка (text, verdict). Что
      обдумать: - где проходит граница: один вызов `run(ctx)` на файл (имя части
      склеивается в `FileResult.files`) или батч целиком на стороне исполнителя;
      `executor/protocol.ts` `files` уже сериализуются, но при батче нужен
      прогресс и отмена; - частичные ошибки: один битый файл не должен ронять
      весь шаг — нужен per-file отчёт, а не один `ToolError` на шаг; - имена
      частей на каждом шаге и Download для набора (сейчас zip по `page.slug`,
      `SchemaToolView.download()`); - обратная сторона: распаковка zip в
      браузере, порядок файлов, поведение many → 1 → many в одной цепочке.
      Зависит от идеи 10 (остальные потребители 1 → many) и идеи 4 (batch по
      архиву), `docs/roadmap.md` фаза 8 «batch-страница».
- [ ] **Идея 17. Промежуточные результаты шагов + выравнивание рядов** — оценка
      M. Два режима просмотра цепочки: - **без выравнивания (по умолчанию):** в
      панели просмотра цепочка изображений по 2 в колонку «исходник → результат
      1 → результат 2 → … → конечный результат»; - **с выравниванием (галочка
      «выровнять инструменты и просмотр»):** у каждого инструмента показаны его
      исходник и результат построчно «параметры — исходник — результат»;
      промежуточные картинки при этом осознанно дублируются на экране —
      результат шага является исходником следующего.
